# LayerForge architecture

How the pieces fit together. For signal-level details see
[DSP.md](DSP.md); for contributor workflow see [CONTRIBUTING.md](../CONTRIBUTING.md).

## One graph, three hosts

```text
              dsp/ (pure JavaScript, Elementary graph builders)
                 │  buildDrumGraph(state, monitorOutput, nativeMidi)
   ┌─────────────┼───────────────────────────────┐
   ▼             ▼                               ▼
Browser       Offline renderer                Native plug-in
(Web Audio    (previews, live-trace           (JUCE 8 + Elementary C++ runtime)
 + Web MIDI)   comparison, WAV export)         VST3 (macOS, Windows) + AU (macOS)
```

- **`dsp/`** has no UI or host dependencies. `parameters.js` owns the patch
  schema, defaults, ranges, validation (`restorePatchState`) and serialization
  (`serializePatchState`). `engine.js` builds the graph, `nodes.js` holds the
  filter, shaper, clipper, saturator and compressor building blocks, and
  `envelope.js` evaluates gain curves.
- **Browser preview** (`npm run dev`) renders with `@elemaudio/web-renderer`;
  triggers come from Space, clicks or Web MIDI. It is the fastest way to work
  on UI and DSP.
- **Offline renderer** (`src/audio/wavExport.js`) uses
  `@elemaudio/offline-renderer` at 44.1 kHz for waveform previews, the sum and
  expanded comparison, and **PREPARE WAV**.
- **Native plug-in** (`native/`) hosts the same UI in a webview and runs the
  same graph in the audio processor.

## Native plug-in

| Piece | Role |
|---|---|
| `PluginProcessor.*` | Audio thread, MIDI, stored samples, host state. Plug-in is a stereo-output instrument that accepts MIDI. |
| Graph worker | A background thread runs the bundled `nativeGraph.js` in JUCE's JavaScript engine, turns the patch into Elementary render instructions and applies them to the runtime. This lets a restored patch **play with the editor closed**. |
| `PluginEditor.*` | Webview editor, file dialogs, preset library, WAV save/clipboard, output meter and trace forwarding. |
| `PluginClipboard_*` | Platform clipboard file references and temporary WAV transfers. |

`native/build/generated/native-graph.js` is generated by
`scripts/build-native-graph.mjs` (run by `npm run build:native`) and embedded
in the binary, as is the production UI from `dist/`. The same script generates
the native host parameter definitions from `PARAMETER_SCHEMA`; IDs and ranges
are part of the plug-in compatibility contract and must not be renamed or
repurposed.

### Host parameters and automation

The VST3/AU exposes 55 continuous, linearly normalized parameters. Stable
IDs are `l0_`, `l1_`, and `l2_` followed by each of `pitch`, `delayMs`,
`attack`, `sustain`, `hp`, `lp`, `clipDrive`, `clipHardness`, `inputDb`,
`width`, `gain`, `phaseOffset`; `noise_` followed by `cutoff`, `q`, `decay`,
`clipDrive`, `gain`; and `master_` followed by `saturationDrive`,
`saturationMix`, `saturationGainDb`, `glueThreshold`, `glueRatio`,
`glueAttack`, `glueRelease`, `glueKnee`, `glueMix`, `glueGainDb`, `drive`,
`hardness`, `ceiling`, `outputDb`. Ranges, units, and defaults are in
`dsp/parameters.js`; glue times are stored in seconds, phase offset is a
fraction of the trimmed sample, and gains without a dB suffix are linear.
Bypasses, mute/solo, sample/trim/envelope editing and routing remain patch
state, not host parameters.

Host parameter values are authoritative over UI snapshots and are overlaid
onto host state, editor snapshots and presets. Older patches import their
values and missing fields use defaults. The worker polls changes approximately
every 20 ms, coalesces intermediate values and updates the shared DSP graph;
automation is not sample-accurate and graph construction/scheduling can add
latency. The editor polls parameter display updates at approximately 16 ms.
The UI reports each discrete edit with a host gesture, rather than one gesture
spanning a drag. Existing DSP smoothing applies where present; sample-based
phase offsets are quantized. Offline previews and exports use the current UI
snapshot, not a DAW automation timeline, and can briefly lag live automation.
Host-specific mapping, automation recording and project restoration require
interactive DAW validation.

### Audio thread and MIDI

`processBlock` converts each MIDI note-on into three per-sample control signals
(gate, one-sample trigger, velocity) at the note's exact block offset. Custom
Elementary nodes (`layerforge-midi-gate`, `-trigger`, `-velocity`) read them,
so triggering is sample-accurate. The processor also publishes an output-peak
value, effect-meter peaks and a lock-free FIFO of output frames and internal
lanes for the editor.

### Monitor outputs

`buildDrumGraph(state, true, nativeMidi)` returns 18 channels in this order:

| Index | Signal |
|---|---|
| 0–1 | Final output, left/right |
| 2 | Browser gate or native one-sample trigger |
| 3–8 | Three processed channel pairs |
| 9–10 | Processed noise, left/right |
| 11–12 | Sum of all sources before bus effects, left/right |
| 13–14 | Saturation input/output stereo peaks |
| 15–16 | Compressor input/output stereo peaks |
| 17 | Linked compressor wet-path gain reduction in positive dB |

The effect taps follow the saved bus order; input/output taps match when an
effect is bypassed, and reduction is zero. Only the first 13 channels enter
live trace capture. The last five are aggregated as maxima between meter
updates, independently of trace capture. The browser worklet sends meter
updates roughly 60 times per second; the native processor accumulates peaks
atomically and the visible editor forwards them on its 16 ms timer.
`layerforgeOutputMeter` carries the final peak and an `effects` array in
13–17 order. Neither path sends effect samples individually to the UI.

Keep the graph, browser channel count/worklet, native scratch buffers and
meter forwarding in sync when changing these lanes. The offline preview
graph uses its own 12-channel layout without the trigger or effect meters;
normal WAV rendering uses only the final stereo pair.

### Host state

`getStateInformation` writes a versioned binary blob: a magic number and
version, the patch JSON, then the referenced mono sample buffers (rate, length,
float data). Up to **six** buffers are stored (three channels × left/right).
`setStateInformation` validates sizes, finite values and exact length before
accepting state, so projects embed the audio and grow with sample length.
The UI theme is part of the patch state.

### UI ↔ processor messages

The UI talks to the processor through JUCE's webview bridge (`window.__JUCE__`).
The UI posts messages such as `sampleTransfer` (chunked 8192-sample transfers),
`midiAudition` and preset or WAV requests. The editor emits events like
`layerforgeOutputMeter`, `layerforgeOutputTrace`, `layerforgePresetList` and
`layerforge:midi` (a DOM event announcing note-ons so the UI can animate).
`src/audio/bridge.js` hides the browser/native difference behind one interface.

## UI

React 19 + Vite. `App.jsx` holds the patch state and orchestrates previews;
`components/` contains the channel strip, knobs, waveform and sum viewers and
the help tips; `audio/` contains waveform math (`waveform.js`), live trace
capture (`liveTrace.js`), the output monitor worklet, diagnostics and WAV
export. Themes live in `uiThemes.js` and `styles/theme.css`.

## Patch data

- A *patch* is JSON: three channel objects, a `noise` object and a `master`
  object. Samples are referenced by key and stored separately.
- `restorePatchState` clamps every value to its documented range and fills
  missing fields with defaults. This is how older patches load (for example,
  patches without saturation or glue restore with those modules bypassed, and
  legacy ADSR-style channel envelopes are converted to envelope points).
- New **`.lfpreset`** files contain the patch and absolute source paths with
  SHA-256 hashes, not sample audio. File contents are checked against the
  loaded audio before saving and checked again before loading. Missing or
  changed files require locating the original; preset loading does not replace
  the current patch until all references are resolved. Version 1 embedded
  presets remain readable. DAW project state still embeds decoded sample audio.
  Preset names are limited to 100 characters; duplicates get a numeric suffix.
- Preset library locations (`userApplicationDataDirectory`):
  macOS `~/Library/LayerForge/Presets`, Windows `%APPDATA%\LayerForge\Presets`.

## Build and release

`npm run build` = `build:ui` (Vite → `dist/`) then `build:native` (generate
graph, CMake, JUCE). Both run `npm run check` first. macOS builds are universal
(arm64 + x86_64). CI and releases are covered in [RELEASING.md](../RELEASING.md).
